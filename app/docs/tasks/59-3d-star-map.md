# Task 59 — A 3D network of star systems

Crates: `rom-mapgen` (universe layout), `rom-sim` (route lengths, transit
positions), `rom-render` and `rom-app` (star-map drawing and navigation),
schema and seed for the star-name table (and a system position if stored), docs. Starts after tasks 67
and 69 are merged (they touch `rom-sim`, `rom-render` and `rom-app`).
Implementer: Claude (Sonnet).

The owner confirmed on 2026-11-16 that the network is 3D and that ships keep
flying freely inside a system. Charged jumps and inhibitors on the routes
between systems come next, in task 70: keep route departure and transit code
easy to extend, but do not build them here.

## Why — the owner (2026-11-15)

"Ultimately the galactic/universal map could be 3D (a 3D network of star
systems)."

Today `rom-mapgen/src/universe.rs` places systems on a disc (`x`, `y`
integers); routes join them and their travel time comes from their length
(`space.route_ticks_per_unit`). Task 57 builds one camera from the street to
the star map and keeps it ready for a third coordinate.

## Build

1. **Systems in a volume.** Systems get an integer height `z` (seeded,
   deterministic, rule 1): a thick disc or a lens, so the network reads as
   3D from an angle yet stays navigable; home systems keep their fairness
   (comparable route distances and neighbours for every player). Routes are
   chosen and measured in 3D (integer length; travel ticks from it).
2. **Simulation.** Route lengths, transit progress and anything that uses a
   system's position use the 3D position. Integers only; iteration in id
   order; determinism scenarios run twice with equal hashes.
3. **Seeing and moving.** The star map is drawn in 3D with task 57's camera:
   orbit around the map freely, routes as lines in space, depth cues (size,
   fade, a faint grid or halo per system's height so the player reads which
   systems are near), picking and hover that work off the plane, ships in
   transit along their 3D routes, fog per system as today. The minimap shows
   a readable projection.
4. **Real star and constellation names (owner, 2026-11-16: "it wouldn't
   hurt to use real constellations and star system names").** Today systems
   get invented syllable names (`names()` in `rom-mapgen/src/universe.rs`)
   and planets are "<system> N". Instead:
   - Star systems take the proper names of real stars (for example Vega,
     Altair, Deneb, Sirius, Procyon, Aldebaran, Tau Ceti, Epsilon Eridani,
     Barnard's Star), each with its real constellation. Use only real,
     astronomical names (IAU proper names or Bayer designations), nothing
     from fiction or games.
   - Systems near each other in the 3D layout share a constellation where
     the pool allows, so regions of the map read as constellations; the star
     map labels each constellation once, faintly, over its systems.
   - Planets are named after their star with Roman numerals in orbit order
     ("Vega II"); resource bodies keep their kind ("Vega belt", "Vega II
     moon" or similar, short).
   - The names are content, not code: a table in the schema and seed
     (generated by `app/db/content/generate.py`, at least 120 stars across
     at least 25 constellations), loaded by `rom-rules`, picked by the seeded
     generator in id order. Document the table in `app/docs/database.md`.
   - Show the names where system and planet names already appear (star map,
     system view, minimap title, tooltips, event lines, selection card).
5. **Data.** If the system position is stored in the schema or the save,
   add the column deliberately (lint views empty, seed loading, documented
   in `app/docs/database.md`).
